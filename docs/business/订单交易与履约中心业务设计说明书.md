## 1. 核心信息（读者必须一眼看懂的三条）

> 验收时拿这三条反问新读者，全为"是"才算合格。

1. **三个业务端（买家端 / 商家后台 / 运营后台）共用一个订单交易中心和一张统一收银台**，不是各画一套交易链路。
2. **支付处理、履约准入是两个不同环节** —— 关卡 A（支付处理）与关卡 B（履约准入）
   必须是**两个独立的判断**，绝不合并成一个框。
3. **订单不能跨渠道随意履约**；但已支付订单被履约准入拒绝后，系统**自动原路退款**并引导用户更换可用规格重新下单，
   **并最终完成最初想购买的那笔订单**（不是退回商品首页、不是钱货两空）。这是全图最重要的业务体验，必须醒目。

## 2. 业务需求

### 2.1 参与角色与基础设施

### 2.2 关卡 A · 支付处理（紫色）

- 买家从买家端选定商品发起下单，交易中心**生成订单并占用库存预占**
- 若尚未支付 → 进入**统一收银台**
- 买家选择支付方式 → 交易中心向支付网关**发起收单**
- 支付成功 → **先通过关卡 B 履约准入**（顺序不可颠倒：准入不过就走不到履约交付）→ 再进入**履约编排流程**
- 对需要二次验证的大额支付 → 完成**支付风控复核**
- 履约准入通过 → **向商家侧交付发货所需的履约结果**

> 图上标记为「关卡 A · 支付处理」，**不得与库存/风控履约准入混为一谈**。

### 2.3 关卡 B · 履约准入（橙色容器 + 红色判断菱形）

- 获取当前订单身份 + 买家**实际选择的履约渠道/收货地址**
- 查询**商品归属及履约渠道准入规则**（连灰虚线到准入规则库）：库存是否充足、该 SKU 是否允许此渠道发货、买家是否在风控名单
- 判断：**当前订单是否满足目标履约渠道的准入条件**
- 满足 → 继续原本的履约编排与发货（绿线）
- 不满足 → 明确提示：**「当前订单无法按所选方式履约，已为你原路退款，请更换规格或收货方式重新下单」**
- 触发**自动原路退款**，允许用户在订单确认页**更换规格/收货方式重新提交**

> **铁律**：支付成功 ≠ 一定能履约发货。履约准入独立于支付处理。
> **关卡 A 与关卡 B 必须是两个独立的 mxCell 容器。**

### 2.4 业务路径

| # | 路径 | 图上表现 |
|---|---|---|
| 1 | **首次下单（未支付）**：发起 → 收银台 → 支付成功 → 履约准入检查 → 通过 → 生成待发货订单并通知商家 | 主链，黑实线 |
| 2 | **支付失败**：扣款失败/超时 → 提示支付未完成 → 重新发起支付 → 支付成功 → **不改变最初的订单内容** | 红虚线小回环（左侧） |
| 3 | **重点：已支付被拒后换规格**（缺货为例）：已支付免重复扣款 → 关卡 B 因库存不足拒绝 → 提示原文 → **自动原路退款**且不离开订单页更换可用规格 → 重新受理 → 重新准入通过 → **回到原订单（原目标完成履约），而非退回商品首页** | 红虚线 + 独立红框区 + 绿线回目标 |
| 4 | **反向场景**：跨境商品走普通渠道 → 被普通渠道准入规则拒绝 → 换用跨境收货方式 → 准入通过 → 返回最初提交的订单完成发货 | 黄色便签说明 |
| 5 | **风控命中转人工**：命中黑名单/异常 → 订单挂起进入运营后台人工审核 → 审核放行 → 准入通过履约；审核驳回 → 退款关单 | 橙虚线分支进运营后台泳道 |

### 2.5 先用后付（独立流程，同一交易履约中心）

1. 买家选择先用后付发起下单 2. 交易中心做信用预授权（不即时扣款）3. 展示先用后付确认页
4. 买家**确认先用后付协议** 5. 交易中心检查该商品/买家是否允许先用后付（准入）
6. 准入通过后，订单进入**先发货、后扣款** 7. 收货确认后交易中心向支付网关发起延迟扣款

> 先用后付与普通支付共用同一个交易履约中心与同一张准入规则库，但有**独立的信用预授权与延迟扣款步骤**。
> 当前作为主图底部的独立横带表达。
