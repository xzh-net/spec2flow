## 1. 核心信息（读者必须一眼看懂的三条）

> 验收时拿这三条反问新读者，全为"是"才算合格。

1. **三个业务端（管理后台 / 门户端 / 设备端）共用一个统一认证中心和一张统一登录页**，不是各画一个中心。
2. **身份认证、应用授权、账号准入是三个不同环节** —— 关卡 A（身份认证与授权处理）与关卡 B（账号准入）
   必须是**两个独立的判断**，绝不合并成一个框。
3. **账号不能跨端随意登录**；但已登录用户被准入拒绝后，可更换正确账号重新登录，
   **并继续访问最初想进入的应用**（不是落到门户首页）。这是全图最重要的业务体验，必须醒目。

## 2. 业务需求

### 2.1 参与角色与基础设施

| 角色/设施 | 职责说明 | 图上颜色 |
|---|---|---|
| 管理端用户 | 持管理端账号，具备管理端业务角色 | 蓝 `#dae8fc` |
| 门户用户 | 持门户端账号，具备门户端业务角色 | 绿 `#d5e8d4` |
| 设备端用户 | 持设备端账号，具备设备端业务角色，支持设备码登录 | 黄 `#fff2cc` |
| 统一认证中心 | 统一登录、身份识别、授权处理、账号准入判断 | 紫 `#e1d5e7`（描边 `#7b4bb5` 3px） |
| 账号与准入规则数据库 | 用户账号、账号归属、角色、应用端准入规则 | 灰白圆柱 |
| Redis | 登录会话及访问过程中的临时状态 | 灰白圆柱 |
| 业务应用 | 管理后台、门户端、设备端各自的业务系统（**BFF 层归入此处，不单独画**） | 蓝/绿/黄 |

### 2.2 关卡 A · 身份认证与授权处理（紫色）

- 用户从任一业务端发起访问，应用将用户带到统一认证中心
- 若未登录 → 进入**统一登录页**
- 用户输入账号密码 → 认证中心**识别用户身份**
- 认证成功 → **先通过关卡 B 账号准入**（顺序不可颠倒：准入不过就走不到授权交付）→ 再进入**授权处理流程**
- 对需要用户授权的请求 → 完成**授权确认**
- 授权完成 → **向业务应用交付访问所需的授权结果**

> 图上标记为「关卡 A · 身份认证与授权处理」，**不得与账号归属准入混为一谈**。

### 2.3 关卡 B · 账号准入（橙色容器 + 红色判断菱形）

- 获取当前用户身份 + 正在访问的**目标应用**
- 查询**账号归属及应用准入规则**（连灰虚线到准入规则库）
- 判断：**当前账号是否属于目标应用允许登录的账号范围**
- 允许 → 继续原本的访问和授权流程（绿线）
- 不允许 → 明确提示：**「当前账号无权登录该应用，请使用对应端的账号」**
- 允许用户在统一登录页面**更换账号重新登录**

> **铁律**：身份认证成功 ≠ 一定有资格进入所有应用。账号准入独立于身份认证和授权处理。
> **关卡 A 与关卡 B 必须是两个独立的 mxCell 容器。**

### 2.4 业务路径

| # | 路径 | 图上表现 |
|---|---|---|
| 1 | **首次访问（未登录）**：发起 → 登录页 → 登录成功 → 准入检查 → 通过 → 进入最初访问的应用和页面 | 主链，黑实线 |
| 2 | **密码错误**：输错 → 提示账号或密码错误 → 重新输入 → 登录成功 → **不改变最初访问的目标** | 红虚线小回环（左侧） |
| 3 | **重点：已登录被拒后换号**（门户账号访问管理后台为例）：已登录免输密码 → 关卡 B 拒绝 → 提示原文 → 不离开登录页更换管理端账号 → 重新认证 → 重新准入通过 → **回到管理后台（原目标），而非门户首页** | 红虚线 + 独立红框区 + 绿线回目标 |
| 4 | **反向场景**：管理端账号访问门户端 → 被门户端准入规则拒绝 → 换用门户端账号 → 准入通过 → 返回最初访问的门户页面 | 黄色便签说明 |

### 2.5 设备码登录（独立流程，同一认证中心）

1. 设备发起设备授权申请 2. 设备展示设备码或用户验证信息 3. 用户浏览器打开**设备验证页面**
4. 用户使用**设备端账号**完成登录 5. 认证中心检查该账号是否允许使用设备端（准入）
6. 准入通过后，用户**确认设备授权** 7. 设备获得授权结果，继续后续业务操作

> 设备码与浏览器登录共用同一个认证中心与同一张准入规则库，但有**独立的设备授权与用户验证步骤**。
> 当前作为主图底部的独立横带表达。

### 2.6 表达禁则（本业务特有）

> 通用禁令（接口路径、类名、框架名、Filter、Handler、Token 内部实现）默认适用，此处不重复。

- ❌ 把授权和准入画成同一个判断框
